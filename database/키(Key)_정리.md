# 키(Key) 정리

## 키(Key)란?

DB에서 **Key**란 테이블에서 행(Row)을 식별하거나, 테이블 간의 관계를 맺기 위해 사용하는 속성(컬럼) 또는 속성의 집합이다.

---

### 1. Super Key (슈퍼 키)

- **행을 유일하게 식별할 수 있는** 속성의 집합
- 유일성(Uniqueness)만 만족하면 됨 → 최소성은 필요 없음
- 예: `{학번}`, `{학번, 이름}`, `{학번, 이름, 나이}` 모두 슈퍼 키

---

### 2. Candidate Key (후보 키)

- 슈퍼 키 중에서 **최소성**까지 만족하는 키
- 즉, 속성을 하나라도 제거하면 유일성이 깨지는 키
- **유일성 + 최소성** 모두 만족
- 예: `{학번}`, `{주민등록번호}` → 후보 키  
  `{학번, 이름}` → 학번만으로도 식별 가능하므로 후보 키 아님

---

### 3. Primary Key (기본 키)

- 후보 키 중에서 **설계자가 선택한 대표 키**
- **NULL 불가**, **중복 불가**
- 테이블당 오직 하나만 존재
- 예: `학번`, `주문ID`

---

### 4. Alternate Key (대체 키)

- 후보 키 중에서 **기본 키로 선택되지 않은** 나머지 키
- 예: 기본 키가 `학번`이면, `주민등록번호`는 대체 키

---

### 5. Foreign Key (외래 키)

- **다른 테이블의 기본 키를 참조**하는 속성
- 테이블 간의 관계(참조 무결성)를 보장
- 참조되는 값은 반드시 부모 테이블의 기본 키에 존재해야 함
- NULL 허용 가능 (선택적 관계 표현 시)
- 예: `주문` 테이블의 `회원ID` → `회원` 테이블의 `회원ID`(PK) 참조

---

### 6. Composite Key (복합 키)

- **두 개 이상의 속성**으로 구성된 키
- 각 속성 단독으로는 유일하지 않지만, 조합하면 유일성 보장
- 예: `{학번, 과목코드}` → 수강 테이블에서 한 학생이 여러 과목 수강 가능

---

### 7. Unique Key (유니크 키)

- 기본 키와 유사하게 **중복을 허용하지 않는** 키
- 단, **NULL은 허용** (기본 키와의 차이점)
- 테이블에 여러 개 존재 가능
- 예: `이메일`, `전화번호` 컬럼에 UNIQUE 제약 조건 부여

---

### 8. Surrogate Key (대리 키)

- **비즈니스와 무관하게 식별 목적으로만 인위적으로 만든 키**
- 주로 `AUTO_INCREMENT`, `UUID` 등을 사용
- 자연 키(Natural Key)와 대비되는 개념

---

### 키 간의 관계 요약

```
Super Key
  └─ Candidate Key (유일성 + 최소성)
        ├─ Primary Key (대표로 선택된 것)
        │     ├─ Natural Key   → 실제 비즈니스 데이터 (주민등록번호, 이메일 등)
        │     └─ Surrogate Key → 인공적으로 만든 식별값 (AUTO_INCREMENT, UUID)
        └─ Alternate Key (선택되지 않은 나머지)

Foreign Key   → 다른 테이블의 PK를 참조
Composite Key → 두 개 이상의 속성으로 구성
Unique Key    → NULL 허용 + 중복 불가
```

## 면접 질문 & 답변

### Q1. Primary Key와 Unique Key의 차이점은 무엇인가요?

| 구분      | Primary Key | Unique Key |
|---------|-------------|------------|
| NULL 허용 | ❌ 불가        | ✅ 허용       |
| 테이블당 개수 | 1개만 가능      | 여러 개 가능    |
| 목적      | 행의 대표 식별자   | 중복 방지 제약   |

> 예를 들어 회원 테이블에서 `회원ID`는 PK이고, `이메일`과 `전화번호`는 Unique Key로 설정할 수 있습니다.

---

### Q2. 후보 키(Candidate Key)와 기본 키(Primary Key)의 관계를 설명해주세요.

후보 키는 기본 키가 될 수 있는 **자격을 갖춘 키들의 집합**입니다.
유일성과 최소성을 모두 만족하는 속성이 후보 키이며, 그 중 설계자가 **대표로 하나를 선택한 것**이 기본 키입니다.
선택받지 못한 나머지 후보 키는 대체 키(Alternate Key)가 됩니다.

> 예: `학번`과 `주민등록번호` 모두 후보 키 → `학번`을 PK로 선택 → `주민등록번호`는 대체 키

---

### Q3. 외래 키(FK)를 설정하면 어떤 제약이 생기나요?

외래 키를 설정하면 **참조 무결성**이 강제됩니다. 구체적으로:

- **삽입 시**: 부모 테이블에 존재하지 않는 값은 자식 테이블에 삽입 불가
- **삭제 시**: 자식 테이블에서 참조 중인 부모 행은 삭제 불가 (기본 동작)
- **수정 시**: 참조 중인 PK 값을 변경하면 오류 발생

---

### Q4. FK 제약 조건을 의도적으로 DB에 걸지 않는 경우도 있나요? 왜 그런가요?

네, 실무에서는 의도적으로 FK를 DB 레벨에서 걸지 않는 경우가 있습니다. 이유는:

1. **성능**: FK 제약이 있으면 삽입/삭제 시마다 참조 무결성 검사가 발생해 성능 저하
2. **유연성**: 대규모 데이터 마이그레이션, 배치 작업 시 제약이 방해가 됨
3. **마이크로서비스 아키텍처**: 서비스 간 DB를 분리하면 FK로 다른 DB를 참조할 수 없음

> 대신 **애플리케이션 레벨**에서 참조 무결성을 직접 관리합니다.

---

### Q5. 복합 키 대신 대리 키(Surrogate Key)를 사용하는 이유는?

복합 키는 여러 컬럼으로 구성되어 **조인 시 복잡도가 증가**하고, FK로 다른 테이블에서 참조할 때 컬럼이 늘어나는 단점이 있습니다.

대리 키(auto_increment ID 등)를 사용하면:

- **단순한 단일 컬럼**으로 행을 식별 가능
- **조인 성능 향상**
- 비즈니스 로직 변경에 영향을 받지 않음 (자연 키는 변경될 수 있음)

> 단, 대리 키는 비즈니스 의미가 없으므로 자연 키도 Unique 제약으로 별도 관리하는 것이 좋습니다.

---

### Q6. 자연 키(Natural Key) 대신 대리 키(Surrogate Key)를 기본 키로 사용하는 이유는?

자연 키는 실제 비즈니스 데이터(주민등록번호, 이메일 등)를 기본 키로 사용하는 방식이고, 대리 키는 식별만을 위해 인공적으로 만든 값(AUTO_INCREMENT id, UUID 등)을 기본 키로 사용하는
방식입니다.

실무에서 대리 키를 선호하는 이유:

1. **변경 가능성**: 이메일, 주민등록번호는 바뀔 수 있음. 바뀌면 이를 참조하는 모든 FK도 수정해야 함
2. **보안**: 민감한 개인정보가 FK로 다른 테이블에 퍼지는 것이 위험
3. **성능**: 짧은 정수(`BIGINT`)가 긴 문자열보다 인덱스·조인 성능이 좋음

> 자연 키는 버리는 게 아니라, `UNIQUE` 제약으로 중복 방지만 걸고 관리합니다.
